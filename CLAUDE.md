# topup-app

Digital top-ups for Ethiopia (game currency, gift cards, keys, subscriptions), priced in birr. Expo SDK 57, expo-router, React Native, Supabase. Customers hold a wallet balance an admin credits; purchases deduct it; **fulfilment is manual** (no supplier ordering integration yet).

## Gifts & redeem codes (feature in 4 parts; all 4 parts done and live 2026-09-27)

Feature: Profile > Gift > "Send to a friend" / "Create a redeem code" -> shop catalog -> buyer pays now; the supplier is called only when the gift is CLAIMED. **Built in Part 1** -- migration `20261016090000_gifts_and_redeem_codes.sql` (forward-only, purely additive, re-runnable), tests `supabase/tests/gifts.test.mjs` (75 checks, in `run.mjs`), live proof `scripts/gift-concurrency-live.mjs` (+ `.sql`; `node --env-file=.env scripts/gift-concurrency-live.mjs`, throwaway `giftrace-*` accounts, self-cleaning).
- **`redeem_codes`**: `id, code (unique, ^[A-Z0-9]{10}$), order_id (unique, -> orders, ON DELETE RESTRICT), product_id, option_id, created_by, status ('active'|'redeemed'|'expired'), redeemed_by, redeemed_at, expires_at, created_at`.
- **`gifts`**: `id, order_id (unique, RESTRICT), product_id, option_id, sender_id, recipient_user_id, redeem_code_id (unique, nullable: set when the gift came from redeeming a code), status ('pending'|'claimed'|'expired'), player_fields jsonb (normalized buyer fields given at claim), claimed_at, expires_at, created_at`. `option_id` is stored besides `product_id` because price and delivery are per pack.
- **`redeem_code_attempts`** (`user_id, ip, succeeded, created_at`, never the tried code): the rate-limit log.
- **Payment link = `orders.id`.** An order is the payment record here (provider, reference, mode, wallet ledger row via `wallet_transactions.order_id`). One paid order backs exactly one gift OR one code.
- **Code**: 10 chars from `ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789`, `generate_redeem_code()`: CSPRNG via `gen_random_uuid()` (pg_strong_random), only its 13 fully random bytes, rejection-sampled (bytes >= 252 dropped) so there is no modulo bias. `create_redeem_code` retries on a code collision (up to 50, a failure is effectively impossible); tested by forcing two collisions.
- **Expiry**: `public.gift_ttl()` = `interval '90 days'` (the one place to change it). Redeem/claim check `expires_at > now()` in the same UPDATE; `expire_gifts_and_codes()` (service_role) sweeps statuses; nothing schedules it yet (no pg_cron). **Refund on expiry: OPEN decision, not built.** A redeemed code's gift gets its own 90 days from redemption.
- **Creation**: `create_redeem_code(order_id)` / `create_gift(order_id, recipient_uuid)` -- INTERNAL (no role may call them; Part 2's SECURITY DEFINER purchase function will). They require the order `status = 'paid'` (captured), a single pack (order.option_id, or exactly one order_items line with quantity 1), the pack/region/product still on sale (`pack_unavailable`), and no gift/code already on the order. Errors: `order_not_found, order_not_paid, order_already_gifted, order_not_giftable, pack_unavailable, recipient_not_found`.
- **Redeem**: `redeem_code(text)` (authenticated) -> jsonb, never raises (so the attempt log commits): `{ok:true, gift_id}` | `invalid_code` (not found / expired / malformed / redeemed by someone else -- ONE answer so guesses learn nothing) | `already_redeemed` (only when the CALLER redeemed it: a double tap; they already hold it, so it leaks nothing) | `too_many_attempts` | `not_authenticated`. Input is upper-cased with spaces/dashes stripped. Redeeming turns the code into a pending gift for the redeemer; claim is the only delivery point for both kinds.
- **Claim**: `claim_gift(gift_id, fields jsonb)` (authenticated) raises one distinct error per case: `not_authenticated, gift_not_found, gift_not_yours, gift_already_claimed, gift_expired, pack_unavailable, player_id_required, id_fields_invalid, id_not_validated, id_validation_expired, region_unverifiable, region_unverified, region_mismatch`. The player-ID rules are checkout's (below), all checked BEFORE the status moves.
- **Atomic pattern (both)**: one conditional `UPDATE ... SET status=... WHERE <key> AND status='active'|'pending' AND expires_at > now() RETURNING` and act only if a row came back. Concurrent callers queue on the row lock and re-check the WHERE against the committed row, so exactly one wins. **Read-then-write is NOT safe**: two callers can both read 'active' before either writes, and both "win".
- **Backstops**: `redeem_codes_guard` / `gifts_guard` triggers make redeemed/claimed/expired final and the identity columns immutable (FK actions at trigger depth > 1 excepted); `gifts.redeem_code_id` unique (a code can never become two gifts); shape checks tie status to redeemed_at/claimed_at; `orders_gift_backed_guard` freezes a gift/code's order at 'paid' (admin_deliver_order / admin_set_order_status failed/refunded / any status write -> `gift_order_locked`); `attemptFulfillment` skips `gift_order` BEFORE any supplier call (`giftBacked` in `_shared/fulfillment.ts` / `fulfillmentDb.ts`).
- **Rate limit**: `redeem_limits()` = 10 failed tries per user, 30 per client IP (from PostgREST's `request.headers`: `cf-connecting-ip`, else first `x-forwarded-for`; best effort), per 10 minutes. Same shape as `claim_id_validation_slot` / `id_validation_attempts` (the only per-user limiter that existed).
- **RLS**: customers SELECT only (codes: creator or redeemer; gifts: sender or recipient; attempts: nobody). No customer writes; everything goes through the functions.
- **Proven**: PGlite suite (sequential semantics, every error, backstops, rate limits, nothing delivered). Live: 8 accounts racing one code -> 1 winner/7 `invalid_code` (x3); one account's 8 simultaneous taps -> 1/7 `already_redeemed` (x2); 8 simultaneous claims -> 1/7 `gift_already_claimed` (x2); all requests in flight together; afterwards one gift per code, orders still 'paid', no vault code.

## Decisions (do not reopen)

- One product maps to many supplier categories. Region = label + buyer form + chip. **The region lock lives on each package**: `region_locked` + `account_region_codes`; a locked package with no codes can never go live.
- Supplier category, offer id and USD cost are per package, in admin-only tables (`product_region_supplier`, `product_option_supplier`); customers cannot read them.
- **Free Fire launches with MENA diamonds only.** No memberships (see "Supplier facts"). No test orders until the app can take payment.
- ID validation goes through the `validate-id` Edge Function only. It writes an `id_validations` record; **`purchase_product_option(option, delivery, id_checked)` refuses a validated region without a matching record** (this user, this region, exact fields, under 15 minutes). A locked package sells only if the record's account region is in its codes; unknown region = refused. Regions the supplier can't validate need the tick, stored as `orders.id_self_declared_at`. Orders store `validation_id`, `validated_account_region`, `validated_player_name`.
- A timeout, error, invalid ID or expired check keeps Continue **off**; Retry is offered. The client never sends a price.
- Player names render as-is, one line with an ellipsis, never sanitized.
- Password-login categories and "first purchase only" offers are blocked in the database with no override. **Never collect game passwords.**
- **The supplier catalog is cached in `supplier_catalog` (admin-only RLS; only the function and the seed script write it).** Search reads the table, never the supplier, so import keeps working after the trial. Packs and USD costs are saved per category with their fetch date, shown next to every price. **Seeded 2026-09-20 (re-run any time, never overwrites newer packs):** `node scripts/fazer-seed-cache.ts`, then run each `scripts/out/seed-cache/NN.sql` with `npx supabase db query --linked -f` (15 files; safe to re-run, never overwrites newer packs). "Refresh catalog" in the import screen re-lists it live.
- **Import region defaults (do not guess a code):** a region is supplier-ID-checked only if it matches one of the 5 checkable games (strict id + name + stated region match, in `_shared/catalog.ts`) and its buyer form maps onto the check's form. It is region-locked only if checked, region stated and not "Global"; gift cards never. `ME` is prefilled for MENA only (`KNOWN_ACCOUNT_REGION_CODES`); every other locked region imports with no codes and stays off until typed.
- New products, regions and packages start OFF. Placeholder prices are `9999`.
- Web tests are not enough for native: on Android the native `Switch` ignores `pointerEvents`, so `components/ui/Toggle.tsx` gives it its own `onValueChange` (guard test in `Toggle.test.mjs`).
